# 미니 PJT: 연금저축 ETF 비교 분석 Agent

## 무엇을 푸나
연금저축 계좌로 ETF에 투자할 때 "무엇을 살 수 있고, 같은 기준으로 비교하면 어떤지"를 한곳에서 보기 어려워 한 번 판단에 약 2시간이 걸리는 문제를, 매수 가능 종목만 실제 시세로 계산한 비교표와 문서 근거로 수 분 안에 답한다.

## 활용한 패턴 (Day 1~7)
- Day 1: 구조화 출력 — 최종 답변을 pydantic `FinalAnswer{answer, comparison_table, sources, base_date}` 로 받는다. LLM(Haiku)은 설명 문장과 표에 넣을 종목코드만 고르고(`with_structured_output`), 숫자는 코드가 도구 결과에서 옮긴다
- Day 2: RAG — 매매 규칙·기초지수 문서를 `MarkdownHeaderTextSplitter` 로 헤더 단위 분할하고, Chroma(Titan 임베딩) + BM25(`kiwipiepy` 형태소) 를 `EnsembleRetriever`(0.3/0.7) 로 결합한다. 검색 결과에 `[출처: 파일 > 섹션]` 을 붙여 반환한다
- Day 3: ReAct 에이전트 — 도구 5개(검색·매수 가능 판정·수익률 계산·자산군 대표 비교·문서 검색)를 에이전트가 질문에 맞게 골라 호출한다
- Day 4: 도구 설계·에러 처리·trace — 독스트링에 "언제 쓰고 언제 쓰지 않는지"를 적고, 시세·문서 조회 실패는 예외 대신 "지어내지 말고 실패로 안내" 메시지로 반환한다. LLM·도구 호출은 콜백 트레이서로 단계별 기록한다
- Day 5: `create_agent` + 미들웨어 — 입력 가드레일(정규식 → Haiku 인젝션 판별), 도구 호출 제한, 출력 가드레일(금지 표현 → 1회 재생성 → 고정 문구), 로깅. 개인정보 마스킹은 trace 에 원문이 남지 않도록 에이전트 호출 전에 적용하고, 체크포인터로 화면 대화를 이어간다
- Day 6: (적용 안 함) Supervisor — 도구 5개라 단일 에이전트로 충분하다. HITL(Day 5)도 매매 주문을 빼서 승인할 위험 작업이 없다
- Day 7: LLM 심사·누적 평가셋 — 고정 루브릭 judge(Haiku) 위에 코드 판정(도구 호출·금지 항목·수치 정확도·정책 위반)을 둔 채점 스크립트와 RAGAS 4지표

## 아키텍처
```
화면(index.html) / POST /query  ──  FastAPI (src/api.py)
  → 개인정보 마스킹 (계좌번호·주민번호·전화·이메일)
  → create_agent (Sonnet 4.6) + 미들웨어 [입력 가드레일 → 도구 호출 제한 → 출력 가드레일 → 로깅] + 체크포인터
       ├─ search_etfs               KRX ETF 목록 CSV + 자산군 매핑 + 매수 가능 판정 + 시가총액 정렬
       ├─ check_pension_eligibility 추적배수 규칙 (레버리지·인버스 불가) + 근거 출처
       ├─ calc_performance          pykrx 시세 스냅샷 → 1년·3년 가격수익률·연환산 변동성
       ├─ compare_asset_classes     자산군별 대표 ETF (매수 가능 종목 중 시가총액 1위)
       └─ retrieve_docs             하이브리드 검색 (Chroma + BM25) → [출처] 붙은 문서 조각
  → 구조화 단계 (Haiku): 설명 문장 + 표에 넣을 종목코드
  → 코드가 비교표 생성, 기준일·정의·면책·근거 문서 부착, 금지 표현 재검사
  → {answer, contexts, trace} (+ 화면용 comparison_table, thread_id)
트레이서 콜백: LLM·도구 호출을 단계별로 logs/trace.jsonl 에 기록
```

## 트라이앤에러 회고
### 시도했지만 실패한 접근 · 왜 실패했는가
- **데이터 수집**
  - pykrx 로 ETF 전종목 목록을 조회하려 했으나 KRX 로그인이 필요해 실패했다. 로그인 없이 쓰기 위해 KRX 정보데이터시스템 CSV 다운로드본으로 전환했다.
  - 투자설명서 PDF를 모두 RAG에 넣는 안을 검토했으나, 보수 같은 수치는 CSV에 이미 있어 문서 검색이 맡을 일이 없었다. 문서는 매매 규칙과 지수 설명만 공개 자료로 정리했다.
  - 매매 규칙 문서를 증권사(삼성증권) 홈페이지에서 수집하려 했으나 자바스크립트 렌더링이라 본문을 받지 못했다. 레버리지·인버스 제한은 증권사 공통 규칙이므로 금융위원회 보도자료와 운용사 안내로 출처를 바꿨다.
- **자산군 분류와 검색**
  - 미국 주식 판별에 "다우존스" 키워드를 쓰자 "Dow Jones Taiwan" 이 미국 주식으로 분류됐다. 다우존스·러셀은 지수 산출사 이름이라 판별 키워드에서 뺐다.
  - "S&P500" 을 기초지수명만으로 검색하자 커버드콜·주식채권 혼합 상품이 상위에 섞였다. 수익 구조가 달라 같은 표에서 비교하면 왜곡되므로 기본 검색에서 제외했다.
- **수치 정확도**
  - 답변 문장에 수치를 직접 쓰게 두자 총보수 0.004% 를 0.04% 로 옮겨 적는 전사 오류가 났다.
  - 도구 결과의 총보수를 단위 없는 숫자(`"fee": 0.006`)로 넘기자 LLM이 비율로 읽어 "0.6%" 로 100배 틀리게 썼다. 필드 이름과 값에 단위(`fee_pct`, "연 0.006%")를 붙여 해결했다.
- **프롬프트만으로 형식 강제**
  - 출처·대표 선정 기준·개인정보 안내를 프롬프트로만 요구하자 구조화 단계(LLM)가 매번 일부를 빠뜨렸다. 필수 문구는 코드가 답변에 붙이는 방식으로 바꿨다.
- **가드레일**
  - 금지 표현을 단순 문자열로 검사하자 "사세요라고 할 수 없다" 같은 부정문도 걸려 정상 답변이 고정 문구로 대체됐다. 프롬프트에 "부정문·인용으로도 쓰지 않는다"를 넣어 완화했지만 문자열 검사의 한계는 남는다.
  - 개인정보 정규식에 `\b` 를 쓰자 한글이 바로 붙은 "678901이고" 를 잡지 못했다. 앞뒤 숫자 경계로 바꿨다. 이때 채점 스크립트가 judge 에 원문을 넘겨 판정 근거에 계좌번호가 남는 문제도 발견해 마스킹된 입력만 넘기도록 고쳤다.
- **평가**
  - RAGAS answer_relevancy 를 기본 프롬프트로 계산하자 역생성 질문이 영어로 나와 한국어 원 질문과의 임베딩 유사도가 낮게 나왔다(문항 3: 0.36). Titan 기준 같은 뜻의 한국어 문장 쌍은 0.69, 한·영 쌍은 0.36 이었다. 질문을 답변과 같은 언어로 만들라는 지시 한 줄을 덧붙여 0.69 로 정상화했다.
  - 인-아웃 세트의 `expected_tools` 를 "이상적인 호출 순서"로 적었더니, `search_etfs` 가 이미 매수 가능 판정을 포함하는데도 `check_pension_eligibility` 를 따로 요구해 맞는 답변이 실패했다(1차 문항 1·5). 실제로 필요한 도구 기준으로 고쳤다.
  - 수치 정확도 검사가 답변의 모든 `N%` 를 도구 결과와 대조하자, 문서를 인용한 "100% 완벽한 헤지는 어렵다" 까지 오류로 셌다(2차 문항 11). 검사 대상 구분이 필요하다는 점을 확인했다.
- **운영**
  - 공용 계정의 Bedrock 일일 토큰 한도에 Sonnet 4.5 가 `us.`·`global.` 모두 걸려 1차 라운드가 10문항에서 멈췄다. 한 라운드 안에 모델이 섞이지 않도록 에이전트를 Sonnet 4.6 으로 바꿔 15문항을 다시 실행했고, 2차도 같은 모델로 고정했다. 문항별 결과를 즉시 저장하고 끝난 문항을 건너뛰는 구조 덕분에 한도에 걸려도 재시도만으로 라운드를 마칠 수 있었다.

### 최종 채택한 접근 · 왜 그것으로 갔는가
- **비교표는 코드가 만든다.** LLM은 설명 문장과 표에 넣을 종목코드만 고르고, 숫자는 도구 결과에서 코드가 그대로 옮긴다. 수치 정확도를 프롬프트가 아니라 구조로 보장하기 위해서다. 2차 라운드에서 비교표 수치 불일치는 0건이다.
- **평가 모드 기준일 고정과 스냅샷.** 기준일을 2026-11-03 으로 고정하고 후보 종목의 시세·시가총액을 저장해 쓴다. 1차·2차 평가에서 같은 질문에 같은 수치가 나와야 개선폭을 비교할 수 있기 때문이다.
- **계산·규칙 판정은 파이썬, LLM 판정은 그 위에.** 매수 가능 여부는 추적배수 규칙으로, 수익률·변동성은 pandas 로 계산한다. 채점도 도구 호출·금지 항목·수치·정책을 코드로 먼저 판정하고, 코드로 볼 수 없는 기대 특성만 고정 루브릭 judge 가 판정한다.
- **개인정보 마스킹은 에이전트 호출 전.** 미들웨어(`before_model`) 시점에는 원문이 이미 그래프 상태와 trace 콜백에 들어가므로, `run()` 에서 먼저 마스킹해 답변·trace·로그·평가 결과 어디에도 원문이 남지 않게 했다.
- **단일 에이전트 + 미들웨어.** 도구가 5개라 Supervisor 멀티 에이전트는 필요하지 않았고, 매매 주문 기능을 빼서 HITL 로 승인할 위험 작업도 없다. 대신 입력·출력 가드레일, 도구 호출 제한, 로깅을 미들웨어로 붙였다.
- **개선 루프는 한 번에 하나.** 실패 문항 하나를 골라 답변 문제인지 판정 기준 문제인지 먼저 진단하고 한 가지만 고쳤다. 판정 기준을 고쳐 늘어난 통과(+2)와 답변을 고쳐 늘어난 통과(+2)를 리포트에 나눠 적어, 기준 완화로 점수만 오른 것처럼 보이지 않게 했다.

### 남은 한계 · 향후 개선 방향
- 수익률이 분배금을 뺀 가격수익률이라 배당형 상품이 불리하게 보인다. 총수익률(분배금 재투자) 계산을 추가할 수 있다.
- 시가총액이 기준일 값이 아니라 수집 시점(2026-11-05 장중) 값이다.
- 평가 모드는 후보 19종목만 시세가 있어, 그 밖의 종목은 "시세 미저장" 으로 안내한다. 실행 시점에 시세를 받는 평소 모드(TASKS 8-1)가 남아 있다.
- RAGAS faithfulness 가 0.54 로 목표(0.80)에 못 미친다. 평가 입력 contexts 에 문서 조각만 들어가 도구 결과에 근거한 문장이 근거 없음으로 집계되기 때문이다. 도구 결과 요약을 contexts 에 함께 넣는 방식을 검토한다.
- 수치 정확도 검사에서 검색 문서에 그대로 있는 숫자는 대조 대상에서 빼야 한다(2차 문항 11 오탐). 문항 7 의 기대 도구도 "종목 조회 도구 중 하나"로 완화할 필요가 있다.
- 금지 표현 검사는 문자열 기반이라 문맥(부정문)을 구분하지 못한다.
- 화면의 대화 기록은 서버 메모리(`InMemorySaver`)에만 있어 재시작하면 사라진다.
